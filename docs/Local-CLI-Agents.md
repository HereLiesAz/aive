# Local CLI agents

The vendors' own command-line tools (`claude`, `codex`, `gemini`, `qwen`) can do the work of a creature. The app **drives** them headless; it does not offer a command line of its own. They run under whatever login you already have on the computer, so the app needs and keeps **no API key** for them, and a subscription you already pay for covers the work. On the desktop it runs the programs you installed; on an Android phone it runs them hidden inside the app (see [On a phone](#on-a-phone-the-hidden-linux-runtime)). The web cannot run a program.

Turn one on in **Keeper's room › Local agents**. It is off until you do. It then appears as a provider (named "Claude Code (CLI)" and so on) that a role can prefer: **Work › Provider** on a creature, or the role's form.

## What the app does when one runs

1. **Only after you approved a plan.** A creature that uses a CLI must have Approval on. The engine drafts a plan ("Run Claude Code headless in an isolated worktree... Nothing is sent to it until you approve this"), you approve it, and only then is the CLI started with that plan. Without an approved plan the task fails and says how to fix it.
2. **In its own copy of the repository.** A fresh `git worktree` of the committed `HEAD` of the linked **Local** repository, on a new branch `aive/cli-<task>-<id>`. Your checkout and its index are never touched. Uncommitted changes in your checkout are not seen (the CLI works from `HEAD`).
3. **With a bare environment.** Only `PATH`, `HOME`, locale, the temp and XDG folders, proxy and certificate variables, and the variables the CLI needs to find its own login (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, ...). No `GIT_*`, no repository-host tokens, and **no vendor API-key variable** unless you turn on "Passing its key variable" for that CLI.
4. **Without the CLI's guard rails off.** The app never passes a flag that skips a CLI's own permission checks or lifts its sandbox (`--dangerously-skip-permissions`, `--yolo`, `danger-full-access`, and the like): `CliAgentSpecs.FORBIDDEN_FLAGS`, enforced by a test over every spec in every mode.
5. **With the prompt on stdin** where the CLI allows it, so it is not in the process list. The prompt says plainly that everything under CONTEXT is material, possibly from untrusted sources, never instructions.
6. **Read-only unless the role writes.** A task whose role needs repository write may edit files; every other task runs the CLI read-only and anything it leaves is discarded.
7. **Committed to a branch, nothing more.** Edits are committed to the new branch (hooks off, a fixed identity) and shown as a `CodeChange` artifact with the branch and commit. Nothing is merged, pushed or released; that stays a person's decision behind the usual approval. A change to `.gitattributes`, `.gitmodules` or `.git` fails the task and is discarded.
8. **Stopped and cleaned up.** A 30-minute timeout, the whole process tree ended on timeout or cancel, the worktree removed, and the branch deleted when it holds no commit.
9. **Read as untrusted text.** Output is read line by line, bounded and scrubbed of key-shaped strings before it is shown or stored; the CLI's own final message is the task's text artifact.

| CLI | Headless form | Edits | Notes |
|---|---|---|---|
| Claude Code | `claude -p`, stream-json, prompt on stdin | `acceptEdits`; allowed tools Read, Glob, Grep, Edit, Write; Bash and web tools disallowed | No shell, so it only edits files. Read-only uses `plan`. |
| Codex | `codex exec --json -C <tree> -`, prompt on stdin | its own `workspace-write` sandbox (commands inside the tree; its network setting is Codex's own, not set by the app); `read-only` otherwise | The only one that claims shell execution and testing. |
| Gemini CLI | `gemini --approval-mode auto_edit -p <fixed sentence>`, task on stdin | file edits approved; shell not (denied headless) | Output is plain text. |

| Antigravity | `agy --output-format text -p <prompt>`, prompt as an argument | none from the app: headless, a tool that needs approval is denied, so it reads and answers unless your own Antigravity settings allow more | Read-only here; the app never passes `--dangerously-skip-permissions`. Some versions printed nothing when stdout was a pipe: Test shows it. |
| Grok Build | `grok --no-auto-update --cwd <tree> --output-format plain --allow Read --allow Grep [--allow Edit] --deny Bash --deny WebFetch --deny WebSearch -p <prompt>` | Edit tool only; shell and web denied | `XAI_API_KEY` may be passed if you choose. Never `--always-approve`. |

A CLI that has an npm package shows **Install** when it is missing: one `npm install -g <package>`, run when you press it. Adding another CLI is adding a spec (`CliAgentSpecs`): its binary, its headless flags, how to read its output.

## On a phone: the hidden Linux runtime

The Android app runs the same CLIs, hidden, with no second app and no terminal. Keeper's room › Local agents shows a status line on each card in plain words ("Downloading the Linux runtime (34%)...", "Installing Gemini CLI...", "Not installed yet", "The Linux runtime is not available in this build") and a button to **remove the runtime** (which also cancels a download in progress). Nothing is downloaded until the keeper presses **Install** on a CLI or its **Test**.

**What it is.** Termux's own pinned bootstrap (`bootstrap-2026.08.16-r1+apt.android-7`, aarch64, SHA-256 `ed83429f...e8f0` in `AndroidCliRuntimePins`), downloaded from Termux's GitHub release into the app's private files (`files/cli-runtime/`), checked against the pin, unpacked into a staging folder, verified (`bin/bash`, the dpkg database) and renamed into place. Its base packages (`git`, `openssh`, `ripgrep`, `nodejs-lts`) come from Termux's own repository through its `apt`, which verifies the repository's signatures with the keyrings inside the pinned bootstrap. Each CLI is then one `apt-get install` (Codex is a Termux package) or one `npm install -g name@version` (`CliAgentSpec.androidInstall`), run only when the keeper presses Install. The CLIs a phone offers are those with an install route: Claude Code, Codex, Gemini CLI, Qwen Code, Antigravity (a community build), Copilot CLI, Amp and Kilo Code. Grok Build, Cursor, OpenCode and Aider have no known Android route and are not offered there.

**How it runs.** Android 10 and later (target SDK 29 and up) will not `execve` a program from an app's writable storage, so the app cannot start the downloaded bash or node directly. It ships **proot** (Termux's own package, with its loader, `libtalloc` and `libandroid-shmem`) as native libraries in the APK, which is the one place an app may execute from, and runs everything under it with the private Termux tree mapped to `/data/data/com.termux/files/usr`, the path its programs expect (so no relocation is needed). The proot libraries are fetched at build time and SHA-256-checked by `androidApp/build.gradle.kts` (`fetchAndroidProotRuntime`); a build without them says "The Linux runtime is not available in this build". Only `arm64-v8a` has them: on another ABI the runtime is not offered.

**What runs with what.** The same pure script builder as the desktop's checks ([`CliRunScript`](../shared/src/commonMain/kotlin/com/hereliesaz/geministrator/providers/cli/CliRunScript.kt), tested): the same forbidden-flag refusal, the project-settings refusal, an escaping-symlink refusal, a bare environment (`env -i`; only the proxy and certificate variables, the CLI's own login variable and, if the keeper chose, its key variable), a timeout, hooks off, a fixed commit identity, bounded output, and a delimited result block parsed by `CliRunResultParser`. The CLI works in a fresh `git clone --depth 1` of the linked GitHub or GitLab repository inside the runtime, on a new `aive/cli-...` branch. It runs only after an approved plan, like the desktop.

**How a creature's repository reaches it.** By address: the runtime's git clones the linked repository's `remoteUrl` (or `https://github.com/<owner>/<name>.git` and the GitLab equivalent). A repository that exists only on the phone (a Local one with no remote) is not reachable by the runtime, and the task says so. A public repository clones anonymously. A **private** one needs the token: the app already holds the keeper's repository token for its own API calls and passes it **only if the keeper turned on "Passing keys" for that CLI**, as a one-shot environment variable (`AIVE_GIT_TOKEN`) of that one process, used by git as an HTTP header scoped to that repository's host, unset after the clone, never in a command line, never on disk, and not in the CLI's environment (`env -i`). Without it a private repository fails to clone and the task says to turn the option on. Delivery is a **patch**: the checkout is deleted when the run ends, so the change comes back as a `CodeChange` artifact (the diff against the base, bounded to about 45 KB and marked when cut) with the branch name and commit it was made under, not as a branch on the phone.

**Privileges.** The runtime is the app's own sandbox: no permission beyond `INTERNET`, no storage permission, no other app. It uses several hundred megabytes of private storage (about 1.5 GB is required free to start) and is removed with the button, or by clearing the app's data. The CLI runs as the app's Android user and can reach the whole runtime and the network.

**Not run on a device.** Written without a phone to run it on. Everything pure (quoting, the builder, the parser, the flag refusals, the install recipes) is unit tested, and the generated script was run under a real bash against a local repository and a fake CLI. Not verified: proot's flags on any Android version (they follow Termux's `termux-chroot`; `PROOT_NO_SECCOMP=1` is set for safety and costs speed), Termux's bootstrap second stage under an app user id, `apt` inside proot, node and git speed, whether Play accepts the proot libraries, and every install recipe except as noted. The install routes follow the design reference's catalogue: Codex and Ollama are Termux packages; Gemini CLI is a JavaScript bundle; **Claude Code is pinned to 2.1.112**, the last release that is JavaScript (later ones ship a native program with no Android build), so it is older than the current one; **Antigravity is a community repackaging** (`@bash0816/agy-termux@1.4.12`, not by Google) that downloads and patches Google's release and can update itself. Qwen Code, Copilot CLI, Amp and Kilo Code are listed on the assumption that their npm packages are JavaScript and have not been checked on Android.

**Provenance and licence.** The design (a pinned Termux bootstrap in an app-private prefix, native executables delivered through the APK, a per-CLI install catalogue) follows HG2Gui (github.com/HereLiesAz/HG2Gui, GPL-3.0, same author), which was read as a reference. No HG2Gui source was copied into The Aive (Apache-2.0); only facts (the release tag, URLs, hashes, package names, version pins and the Termux conventions) were reused, and the code here is written separately. The Termux bootstrap and its packages are GPL and other licences and are **downloaded at run time, not bundled**. The proot packages (GPL-2.0-or-later; `libtalloc` LGPL-3.0-or-later) are **bundled in the APK as separate programs** fetched at build time, which needs the notices and source offer in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md). **Open decision for the owner:** whether shipping a GPL program as a separate executable alongside an Apache-2.0 app is acceptable for both flavours (it is a mere aggregation of separate programs, not linked, but it is the owner's call and Play's), or whether the Android runtime should live in a separate module or app.

Open points: proot may prove too slow for npm and git; the alternative is HG2Gui's direct route (bundling the bootstrap's own programs as native libraries and a preload library), which is larger. Usage (tokens, cost) is not reported on a phone. The prompt builder is copied from the desktop's (`AndroidCliAgentProvider.kt`) because the desktop's lives in its own module; moving it to `shared` is a follow-up.

## From a terminal

`aive agents install|enable|disable|test <id>` does the same as the Keeper's room buttons, from the `aive` command line ([CLI](CLI.md)). It is local only: it needs an attached interactive terminal and `--yes` or a typed confirmation, and it is not reachable from the control API, MCP or any HTTP route, so an agent holding the token cannot install, enable or run a vendor CLI. The settings store and the install/test/status host live in `shared` (`desktopMain`), used by both the desktop and `aive`. `aive agents` alone lists them, read-only. The headless engine does not yet run enabled CLI agents as providers.

## Test, and what is not verified

**The flags were written from each CLI's documentation. They have not been run against every version of every CLI by the people who wrote this.** That is why each CLI has a **Test** button: it runs the installed CLI read-only in an empty folder on a tiny prompt ("Reply with the single word OK") and shows what happened: the answer, or the exit code and the CLI's own error ("unknown option ..."). A flag that is wrong for your version shows there, not as a failed task, and is fixed in `CliAgentSpecs`. Test sends a real prompt, so it counts against your own plan or quota. Gemini CLI and Qwen Code, whose headless flags have changed between versions, are the likeliest to need a fix.

## Limits and open decisions

- **A CLI is a program that runs as you.** The app confines what it can (a worktree, a bare environment, no bypass flags, the CLI's own sandbox where it has one) and cannot confine the rest: a CLI can read files you can read, outside the worktree, and use its own network and its own configured tools. Codex's sandbox is real; Claude Code and Gemini rely on their tool allow-lists. Prompt-injected context is the main way this goes wrong, which is why a plan must be approved and context is labelled as data. Wrong if you cannot accept that: leave them off.
- **A CLI's own configuration applies.** Its settings, memory files and MCP servers (in your home folder) are loaded by the CLI; a project file in the repository that a CLI reads (instructions, settings) is repository content the CLI may act on. The app does not inspect them.
- **Explicit only.** Auto work never goes to a CLI (it edits your computer). A role must prefer one. Wrong if you want Auto to use them: a switch for that is not built.
- **Terms of service.** Driving a vendor's CLI from a program may be restricted by that vendor's terms for subscription logins. Check yours; the app does not.
- **The branch is the delivery.** Work lands on `aive/cli-...`, not on the run's checkpoint branch the Local workspace agent uses; merging it is yours, through Local Git operations (behind their approval). Wrong if you want it on the run branch automatically.
- **No follow-up messages.** A CLI runs once per task (`sendMessage` is rejected); a correction is a new task or **Run again from here**.
- **Repository-less work** (research with no repository linked) is not supported; a CLI needs a Local repository.
- **Usage** is whatever the CLI reports (Claude Code reports tokens and cost; the others may not).
