# The Keeper's room

The Aive has two places: **the hive**, where all work happens (`Swarm-OS.md`), and **the Keeper's room**, where everything that sets the hive up lives. Consolidating the app into those two places is planned in stages, below; all three are done.

## Parts

| Group | Part | Holds | Was |
|---|---|---|---|
| Feeds the hive | **Connections** | AI providers, remote A2A agents, repository hosts (GitHub, GitLab, Entire) | Settings › AI Providers, Repositories |
| | **Compute** | the compute pool, and which work goes to which machine | Settings › Compute Pool, Compute |
| The keeper | **Projects and data** | project files, the setup file, JSON export and import, delete everything | Settings › Projects, Data, Privacy |
| | **Limits** (wide) | the spend caps: a cost cap per run and an hourly spend cap | This device |
| | **This device** | spend caps (on a phone only), remote access, the A2A server (desktop), the local planner, local orchestration specialists, small tasks on this device | Settings › Remote Access, Local Planner, Local Orchestration |
| | **Delegations** | gates a creature passes without asking, each with Revoke; how many approvals in a row earn an offer | (new) |
| | **Appearance** | the ground, chosen from six swatches; Reduce motion; Always show creature labels | Settings › Appearance |
| | **About and privacy** | crash reports, trace export (OpenTelemetry), diagnostics | Settings › Crash Reports, Diagnostics |

Compute shows only where the build offers distributed compute.

## Delegations

When you approve the same creature's plan on the same provider several times in a row (5 by default) and never reject it, a dialog asks once: "Let it proceed without asking for plan approval?". **Let it proceed** delegates that gate; **Keep asking** leaves it for the rest of the streak. A delegated gate approves itself and its run's events show "Approved by delegation". Only a creature that cannot write to a repository, deploy or write anywhere else, on a provider that cannot either, is ever offered; `HumanApproval` tasks and every other gate always ask (`docs/THREAT_MODEL.md`, Progressive delegation). A rejection starts the streak over and ends the delegation. The Delegations part lists each one with **Revoke**. Delegations stay on this device and are never in the setup file or an export.

Memory is not here: it is a swarm of its own, running beside every other, so it lives in the hive: **Memory** is the last view in the row of a live hive's Timeline (Overview, Waterfall, Events, Memory) and holds the whole Memory swarm screen in place (`RunTimeline(memoryContent = …)`); on a wide window the rail's Memory place opens the same screen as a place of its own. Its stages that run without a model wear the neuron (`Node-Creatures.md`, Programmatic work).

## Layout

- **Wide** (820dp and up): a page title (KEEPER'S ROOM, "Make it yours", one line), then an Ink list of the parts on the left (the open one filled Yellow, a part's count beside it) and the open part on its own Ink card on the right, under its group as the eyebrow, its name and its one-line lead. The spend caps have their own part, **Limits**. Appearance there is a grid of ground cards, three across (swatch, name, SELECTED on the current one), then setting rows, each a line about it and a switch; the whole row toggles.
- **Phone:** there is no Limits part; the spend caps stay at the top of This device.
- **Phone:** the list is its own page; a part opens over it with a "‹ Keeper's room" pill, and Back returns to the list. The header's gear opens the room from anywhere.
- The room remembers the open part (`keeper.section`).

## Connections

One row per thing (`ConnectionRow`): its name, one line about it, its status and what can be done to it. Connected things are Ink rows; things not yet connected are outlined. While no AI provider from the catalog is connected (an agent that comes with a repository host, such as OpenCode through GitHub, does not count), a **Try it free, no key** card offers each keyless gateway in one tap. AI providers not yet connected sit behind one **Add a provider** row rather than a card each, keyless ones first; those have no **Get API key**. On desktop a keyless link holds no secret and is stored without the keychain, so it works on Linux without `secret-tool`. Local Git needs no account: a folder is picked when launching. **Add an A2A agent** takes an Agent Card URL and then an optional token; such an agent runs only for roles that prefer it (`A2A.md`). Drifters let in at the hive's edge are the same connections and are listed here too; disconnecting one here forgets it, as at the edge.

Hive cards (**Share hive card**, **Import hive card**) are described in `A2A.md`.

The choice is stored per device (`on-device.small-tasks.enabled`).

Until a server is always allowed, the first call to it in each run asks the keeper (`docs/architecture/MCP_HOST.md`).

## Appearance

**Ground** is one radio group of six swatches, the current one ringed (`docs/BRANDING.md`, Ground and the shell header). **Reduce motion** (off by default, stored on this device as `aive.appearance.reduce-motion.v1`) holds the creatures and other looping movement still. It is OR-ed with the platform's own signal (Android's animator scale at 0, the browser's `prefers-reduced-motion`, or `AIVE_REDUCE_MOTION` on desktop), so it can turn motion off but never back on against the system; when the device already asks for less motion, the part says so.

**Creature labels** (off by default, stored on this device as `aive.appearance.always-show-creature-labels.v1`): a hive of more than 12 creatures normally shows only the selected creature's label so packed cells stay readable; turned on, every creature keeps its label however full the hive is (`docs/Node-Creatures.md`).

## Inbox

The Inbox page (`LiveInboxScreen.kt`) on a wide window (820dp and up): KEEPER ATTENTION, "Inbox", and **Mark all read**, which marks every item the run lists as seen in the same read record the header's badge counts (`InboxReadLog`), so the badge clears. Under it, an Ink list of everything waiting on you (NEEDS YOU and how many): each entry is its kind (plan or task approval, sub-workflow gate, escalation, question, budget spent), its attempt when not the first, its task and its role, in plan order. The run keeps no time per wait, so no time is shown. The open entry (remembered as `inbox.selected`) fills the Ink card beside it: its creature, faint in the corner, what it says, each artifact it waits with (ARTIFACT WAITING, its label and a line of it) and the real actions, the same calls as the creature's Needs: **Approve plan** and **Reject plan** (asks first), **Approve task**, **Approve** a sub-workflow gate, **Retry task** and **Stop workflow** (asks first). Approving goes through the run's own approval, so every `HumanApproval` still waits for a person (`THREAT_MODEL.md`, invariant 4). A question or a spent budget says where to answer it: on the creature, in the hive. A Hall Monitor pause or a spend cap stop still has its own screen. On a phone the Inbox is unchanged.

Selecting a creature opens its panel, in three tabs (`TechnicalInspector`, `CreatureTab`); the breadcrumb ends on the open one (Hive › a hive › a creature › Mind). Under them, one line gives its state, its provider (when it has one) and its place in the plan, such as "Running · Claude · 3 of 5" (`creatureHeaderLine`, `planPlace`):

- **Needs:** its needs, and what it waits on you for: a plan or task to approve, an escalation, a nested gate, a spent token budget (with **Raise its budget**, which opens its Mind), a question its agent asked you (drawn from the host catalog, `Agent-UI.md`), and messages to its agent. This was the Inbox.
- **Work:** when this creature does several tasks of its role (`CreatureRoam.kt`), first **The same creature, other tasks**: a pill for each, opening that task; **Here** marks the one it is at now. Then its job (`HiveJobEditor`, mockup H4), the task fields that lived in the Workflows form editor: its **Objective** in a well (changed text is applied with **Apply**), its **Acceptance criteria** as rows, each removed with its ✕, and **Add a criterion**; then **Approval** (a person approves, or none; tapping switches), **Retries** (how many tries, then what happens: the hive stops, it asks you, or another creature takes over; tapping steps through 1 to 5 tries) and **Runs on** (this device, any paired device or a chosen device; with paired devices, tapping sends it off this device and back, and a person's approval step never leaves it). ### A creature's provider

An agent creature's Work tab has a **Provider** row under its job (`CreatureProviderRow`): **Auto** (the default), or one connected provider. It reads and writes its role's `preferredProviderId` through the same save path as the Mind (`onSaveRoleCollection`), using the picker the Roster and the Providers screens use (`ProviderChoiceRow`), so the role is the single place a provider is pinned. Because the provider belongs to the role, every creature wearing that role follows it, and the row says so. A creature pinned to an A2A drifter shows that pin by the drifter's name and can be set back to Auto. A task that requires a provider by id (`ProviderConstraints.RequireProvider`) is also shown as pinned, but only its task can change that, so the row shows the note without the picker. Creatures that are not agents (scripts, tests, repository steps, a person's approval) have no provider and no row.

In the terrarium each agent creature wears a small badge at its head: **Pinned: Claude** (Yellow) or **Auto** (Ink), the same `isProviderAuto` rule the engine fails over by. Pinned creatures never switch providers silently: if the provider fails the creature stops and says how to switch. Auto creatures fail over to another connected provider (docs/Orchestration_layer.md). Provider routing never touches approval: `ApprovalPolicy`, `HumanApproval` before mutating repository operations and the validator's ancestor rule are the task's, and neither the row nor the badge reads or writes them.

Drafting a hive (`SwarmDraft`) assigns no providers: it gives each step a `roleId` from the swarm and nothing else, so every drafted creature takes whatever its role already says (Auto unless the keeper pinned that role). That is safe, so it stays; a keeper pins a drafted creature afterwards from its panel.

A creature opens on Needs when it waits on you, otherwise on Work; the open tab survives a restart while the same creature stays open. Waiting on you means a plan or task to approve, an escalation, a nested gate, or a spent token budget, one definition for the badge, the panel and the hive's Owner attention card (shown only then, opening that creature). The header's Inbox badge counts the waits not yet seen and opens the next unseen one, on its Needs; opening a creature's panel marks its wait seen. Only the Hall Monitor's pause and a spend cap stop, which speak for the whole hive, keep a place of their own (`Inbox`).

## First launch

Every launch opens on the hive, not on a form or the Keeper's room (`MindMapRunScreen`, `FirstCreature`): the starters to keep one of, the first picked, and one field, **What should it work on?**, with **Feed it**. Feeding keeps the picked starter and names the hive from the first words it was fed (never from an empty tap). Its name, a repository and saved projects are under Options. Until there is a hive, its places' row is hidden.

Feed it is gated on what the connected agents can reach (`ProviderReach`, `FeedGate`), and the gate sits right above it with its resolution in place:

- **No AI provider:** the free keyless gateways, each a one-tap pill (**Use Kilo Gateway · free, no key**), with the note that a free gateway may log prompts; then a quieter **Use your own key** pill to the Keeper's room. Feed it waits quietly.
- **Every agent works only inside a repository** (OpenCode on GitHub Actions, linked with a GitHub token): the repository fields open above Feed it, offering only the kinds those agents work in, alongside the free gateways for work with no repository.
- **A repository no agent works in:** the fields open there too, to choose another kind, or none.

**The plan is reviewed before the run exists** (`orchestration/PlanReview.kt`, `PlanDecisionOverlay.kt`). When a planner is linked, the plan it drafts is read by the **Adversarial Reviewer** (or, with that role off, the first enabled role that may reject and approve plans). It approves, or sends the plan back with its objections and the planner reworks it, for at most **three reviews**; the launch shows it on a small field of its own (the planner's egg growing, the reviewer hatching from it, then the egg of the plan's first step, gestated by both, which cannot hatch until you start the run; docs/Node-Creatures.md, Planning), with the round it is on. Then you get the final say: **The plan, reviewed** (under that field) shows the plan it ended with (each step, its role, and whether it needs your approval), whether the reviewer approved (and after how many rounds) or never did, and everything the reviewer said, round by round, as plain selectable text. **Start the run** creates the run from that plan; **Do not start** creates nothing. You see it whether the reviewer approved or not, and a plan from a remote request is held for you the same way: only you decide it, in the app. The reviewer is advisory: it decides no approval gate and changes nothing, and a reworked plan passes the same validation as any plan. If it cannot be reached (or the planner cannot rework), the loop stops, the plan so far comes to you with the reason, and the launch is never blocked. The reviewer sees the plan and the objective, goes only to a provider you have linked, and never moves off a provider its role is pinned to. The same review runs on a description drafted into a hive in Build (**Draft**), where what it said arrives as the draft's notes. **A saved hive with an Orchestrator in it is a rough design** (`SavedHivePlanning.kt`): you drew what you want done and the Orchestrator still decides exactly how best to do it. Launched from the hive's **Launch**, the Orchestrator plans from that design (its other tasks are shown to the planner as the plan so far; it may keep, change, add or remove steps), the reviewer reads the plan, and you decide, exactly as above, on the same field. The run is of the planned hive, saved under a new id: the hive you drew is left as drawn, and a step that kept a task's id keeps everything else you set on it (retries, escalation, provider, environment). A saved hive is planned only when everything in it besides the Orchestrator is an agent's task that always runs and needs no approval or the keeper's; one with a script, an action, a repository change, a test run, a task that waits on an outcome or a role's approval launches as it always did, as does any hive with no Orchestrator, and so does a launch with no planner, reviewer or keeper to decide (a remote interface is none of these). A decision left waiting is kept across a restart for a saved hive too, and dropped if the hive or anything else the plan was made from has changed. The starter workflow is not reviewed. A decision you have not made is kept across a restart (`ReviewedPlanStore`, on this device, outside workflow persistence and every export): the next launch of the app offers the same plan and reasons again if nothing it was made from has changed (the objective, repository, runs it continues, the roles the planner may use and the reviewer, compared by a SHA-256 over all of them), and drops it if anything differs or a week has passed. Resuming is not reusing: every new launch, even of the same objective, is planned, reviewed and decided afresh, and the store records no approval, only the decision you were looking at. Run-time gates are asked on every run as before; when a run is rewound (**Run again from here**), the tasks it keeps stay done and what re-runs is gated afresh, with repository changes always. Spend: these calls count against no cap (nothing exists yet to charge them to), which the three-review limit bounds.

Pressing a gated Feed it shows the gate's message and starts nothing. A launch that fails stays beside Feed it, the objective still typed, until the next edit or launch.

## Budgets and spend caps

Three circuit breakers stop spending; none estimates, and only what providers report counts (`SpendCircuitBreakers.kt`).

- **A role's token budget** (its Mind, per run): once the tokens reported for every task of that role in the run reach it, its running sessions are cancelled and its tasks parked (`ROLE_BUDGET_SPENT`), a stopped one as a fresh attempt, and its unstarted tasks do not start. Each waits on you, on its Needs. Raising or clearing the budget releases them at the next cycle; the current role wins over the run's snapshot.
- **A cost cap per run** and **a spend cap per hour across runs** (This device, in US dollars, blank for none; kept on the device, `SpendCapStore`): when the run's known cost, or the known cost reported on this device in the last hour, reaches its cap, every live session is cancelled and the run is stopped (`WorkflowRun.spendPause`, tasks parked as `SPEND_CAP_STOP`). The Inbox shows the stop and **Lift the stop**, which puts every task back where it was; a cancelled session starts again as a new attempt. So raise or clear the cap first: a cap still reached stops the run again (the run cost at its next cycle, the hourly spend when it is next summed: when the run spends, or after a minute).

Cost a provider does not report (keyless and free providers, or ones that report tokens only) never trips a cap.

## The hive's state

A hive that stopped reads **The hive stopped**; one that cannot reach its agents, **The hive can't reach its agents**. Both offer **Try again** and **Connections**; a hive stopped by corrupted data offers only **Delete all projects and runs to recover**. Work no connected agent can take fails as "No connected agent can do this work", with what to connect (`UserFacingError`, `ErrorKind.NoAgent`).

A completed hive shows **What it made** under its run's status: the text artifacts of its final tasks (those nothing depends on), selectable. Once its run has completed, failed or been cancelled, its one follow-up is **Feed it more**, which asks what next and launches a continuation in the same project (`ContinueRunPanel`). A resting hive keeps its objective bar (`HiveLaunchBar`); on a phone a live one has none.

Over a finished swarm it launches the objective at once as its continuation, through the same launch as **Feed it more** (which it replaces here). Over a swarm still running it reads **Queue**: launching then would cancel the running swarm, so the objective is held on this device (`HiveFeedQueue`), shown under the bar with **Take it back**, and started as the continuation once that swarm finishes, wherever the keeper is (`QueuedFeedLauncher`). One objective waits at a time.
- **The creature panel docks** on the right (310dp) instead of rising as a sheet, beside the whole page. Its head reads **CREATURE · i OF n** (its place in the plan) over its job's name, with **Close the creature panel**; Back closes it too. A card shows the creature, its state chip (Working in Yellow, Complete in the clasp green, Waiting on Ink, waiting on you or failed in red), its role and its provider. Needs, Work and Mind are tabs underlined in Yellow. Mind opens with a plain list of what it really is (role, provider when it has one, what it needs to work with, its token budget) before the editors. Needs and Work hold the same as in the sheet.

A new hive (the district's **New hive**, mockup H6) opens empty and in Build (`RestingHive`, `NewHive.kt`). Its head is a pill naming it that surfaces to the district, with Live and Build beside it as one control; the field points at both ways in. Under it, the screen leads with **Describe what the hive should do**: a prompt with a primary **Draft** button, where a keeper drafts the roles and links them for you (see below). Then **Name this hive…** with **Save** (renames the hive's workflow through the workflow library), then **Or build it yourself**: a tray of the swarm's switched-on roles (`NewHiveRoles.kt`). Each role shows its portrait, its name and its one-line purpose; a **Suggested for this hive** group comes first (at most three, `RoleSuggestions.kt`: an empty hive gets a planner and an implementer; a builder with no reviewer or tester gets one; a creature nothing feeds gets the role that usually feeds it; three or more creatures with no orchestrator get one), all read from each role's authorities, never its name. Tapping a role opens a preview sheet (what it does, what it can and needs, what it usually gets work from and hands work to, and why it is suggested) with **Add to hive** and **Close**; only that button, or the separate **+** on a card, adds it unwired, and Undo takes it back out. Edits keep the name given. The objective bar appears once the hive has a creature. Any hive opened with no creatures opens this way. **Closest first** (`ClosestHives.kt`): on a new hive, **Draft** first looks through your saved hives for the ones that speak of most of what you described (names, descriptions, creatures' names and jobs; a few shared words at least; no model) and shows up to three, each with the words that matched and **Use this hive**, which gives this hive that one's creatures as one edit on the tide (one Undo takes them out). Beside them, **See how the planner would do it** runs the draft below. With nothing close it goes straight to the planner, and a hive that already has creatures (Redraft) skips the list. Open decision: this is a word match, not meaning; it is wrong when your wording differs from the hive's, and then the planner is one tap away. **Draft from a prompt** (`SwarmDraft.kt`, `SwarmDraftPanel.kt`): when a keeper is linked, the bench also offers **Or describe it and let a keeper draft it**. The planner (the same one launching uses, offered only switched-on agent roles a provider can staff) proposes at most 12 creatures with strands and a job each; the pure layer checks it (unknown roles, loops, blank or duplicate ids, too many are refused in plain words, never crash), makes every step an agent task, keeps any approval the planner asked for, and the result lands as one edit on the tide, so one Undo empties the hive again. A hive that already has creatures shows **Redraft** instead: it asks (**Replace** / **Keep mine**) and Undo brings the old layout back. A provider failure (out of credit, rate limit, offline) reads as everywhere else, with **Try again**. Drafting never launches a run, touches a repository or loosens an approval (THREAT_MODEL invariant 4); launching a drafted hive goes through the usual launch bar.

## What a role has done

In the Roster (the Swarm's role list) every role has **Show activity**: what that role has done across **every run kept on this device**, in every hive, not only the live one. Above the list, counts: steps, runs, completed, failed or escalated, tokens and cost as providers reported them (a step with none adds nothing, and a cost is shown as "none reported" when no step reported one). Below, one plain, selectable line per step, newest first (at most 40; the counts cover them all): when the run last changed (UTC), the hive, the task, how it ended, its attempt when it is past the first, and its tokens and cost. A step is the role's when its run assigned it, or, with none assigned, when its workflow's task names it. `RoleActivities.of` is a pure function over the saved hives and runs (`RoleActivityTest`); it reads records that already exist and records nothing. The live run's own activity by role is the Log's **All activity** source (see the hive's timeline).

## Pause, change, resume

A live hive's row has **Pause** beside Stop. Paused, nothing new starts (no creature, no system step, no remote compute, and a retry waits); what is already running finishes; no session is cancelled and no task is parked, so **Resume** starts nothing over. The pill reads **Paused · Resume** and the hive says it is paused. Approvals and decisions still go through. It is the run's `keeperPause` (`WorkflowKeeperPause`), kept with the run, so it survives a restart; a spend cap's stop and the Hall Monitor's pause still take effect over it (`ApplicationRuntime.setKeeperPause`, `SpendCircuitBreakerTest`).

Change, with or without a pause: a creature's job and criteria saved from its panel reach the live run when that creature has not started (waiting, ready or about to retry), because the engine reads a task's definition when it starts it (`ApplicationRuntime.applyLiveDefinitionEdit`). A creature that is running or done, a creature's role, executor and strands, and the hive's shape change from the next run. Before this, a save was written over within a second by the runtime's own copy.

**Rewind:** a creature that has started or finished offers **Run again from here** on a live run too, not only a finished one. The live run is stopped (cancelled), what had finished keeps its result, and a new run continues from that creature, so it stops the swarm, though not its history. Open decision: resetting creatures in place, without stopping the rest of the swarm, needs an engine operation that does not exist (a finished creature cannot be reset, `TaskRunTransitions`); this fork is the observable default until it does. Pause is wrong if you meant "park everything now": that is Stop, or a spend cap. Structural edits (adding a creature, rewiring) to a running hive are refused until the next run.

## The hive's timeline

A live hive's **Timeline** pill swaps the hive for its run's timeline, in two views (remembered, `overview.timeline.view`). **Overview**, the way back to the hive, **Flowchart**, **Waterfall**, **Events**, **Memory** and **Log** share one row (`AzphaltTabs(leading = …, trailing = …)`); Memory shows the Memory swarm screen in place, not a view of the timeline, and Log, last, is described below. The row stays fixed under the heading while the view below it scrolls, and the row scrolls the selected view into sight:

- **Flowchart:** the workflow as boxes and arrows, left to right: a step sits to the right of everything it waits on, and steps in a column are ordered by where their feeders sit. Each box carries the step's name, its role (or what kind of executor does it) and, with the run, its state in the same colours as a creature's chip (working in yellow, complete in green, waiting on ink, waiting on you or failed in red). A step a condition skipped (cancelled) is dimmed, not red. An arrow out of a conditional step says when it fires ("if it fails"). Tapping a box selects that creature. It draws `WorkflowFlowchart.of(definition, run)` (a pure function, `WorkflowFlowchartTest`) and edits nothing. It scrolls in both directions.
- **Waterfall** (the default): one row per creature, one bar per attempt, on a shared time axis, so work running in parallel overlaps. Each bar is coloured by phase: Planning, Waiting on you (drawn as a thin pause line: a gate), Running, Verifying, Retrying. A white tick ends a finished attempt, a red one a failed attempt; a bar still going runs to now. Hovering or tapping a bar shows its phases and usage (tokens, cost); tapping also selects its creature. Each bar is one labelled button for screen readers. The bars unroll once on arrival and, while the run lives, grow once a second; with reduced motion they do neither and move only when new events arrive.
- **Events:** the run's events in order.
- **Log** (`RunLogView`, `log/`): the full log, one source at a time, picked from a second row of tabs (remembered, `overview.timeline.log.source`). Oldest line first, newest at the foot; the list follows the foot only while you are there. Each line is its UTC time, whose it is (the task, and the role doing it), and the text, plain and selectable, never rendered as markup. For the sources about the run's steps (All activity, Run events, Agents) a third row of tabs filters by **role**: **All roles**, then each role that acts in what is shown, in the order they first act. The five sources:
  - **All activity:** the run's events and what its agents thought and did, interleaved by time (events first when the time is the same), each line keeping its role. Nothing is dropped or reworded: it is the two sources below in one list (`allActivityLines`). Agent lines are in memory, this launch only.
  - **Run events:** every event of the run, in time order, with the whole reason (Events cuts reasons to 80 characters). From the durable event journal, so it survives a restart. Like Events, it reads the active run (`onLoadRunTimeline`).
  - **Agents:** everything this run's agents thought and did, interleaved by time, from `SessionActivityFeeds`: each line is now dated, and a session keeps its newest 300 lines (was 60). Still in memory only, this launch only, never exported.
  - **App:** the app's own diagnostic lines (`appLog`, `AppLog`): launch refusals and failures, settings failures, store-step failures with their stack traces. The newest 500, dated, kept on this device across restarts (`aive.app-log.v1`), keys scrubbed before they are kept (`ControlRedaction.scrub`).
  - **Memory layer:** what consolidation did, one line per packet it applied, completed, declined or failed, with the workflow it was for (`MemoryLayerController.journal`). In memory only, the newest 500, this launch only: nothing durable records when a queue entry finished. The source is absent where the app has no memory layer.
  Log text is the record's own words, not translated.

A creature's Work reaches it too: **Open its trace** turns the Timeline on and closes the panel, leaving that creature selected on it.

The waterfall is a pure function of the run's event journal (`runWaterfall` in `RunWaterfall.kt`, tested in `RunWaterfallTest`):

~~~
TaskStarted                         -> an attempt begins (Running)
events before it starts             -> it begins early, in Planning
ApprovalRequired, HumanDecisionRequired -> Waiting on you until the decision
work before an attempt's first gate -> Planning (a plan gate follows planning)
ArtifactCreated                     -> Verifying
VerificationFailed, RetryScheduled  -> Retrying, until the next attempt starts
TaskCompleted / TaskFailed / TaskCancelled -> it ends
the run's end                       -> every open bar ends; otherwise they run to now
ProviderUsageRecorded               -> added to the attempt it fell in
~~~

## Removing a creature and deleting a hive

**Remove** (Build, with a creature selected, beside Duplicate; with Cluster on, **Remove N creatures**) takes the creature's task out of the hive together with every strand touching it, as feeder or as fed. A knot that named it goes back to the plain one. It is one step on the Undo history, so one Undo brings back the creatures and their strands. Strands that ran through a removed creature are not bridged: what it fed is left without that feeder, and you wire it again if you want. An edit that would break the hive is refused and nothing changes; taking out the approval ahead of a repository change is one. Removing the last creature leaves an empty hive. While a run of the hive is live, Remove is not offered and the page says why.

**Hive options** (`HiveActionsMenu.kt`): a long press on any hive in the district (the hives list) opens a menu naming it, with **Open** (what a tap does), **Delete hive** and **Close**; a screen reader finds it as the hive's "Hive options" action. Choosing Delete hive does what the red pill below does, asked from here: it looks first and says in a plain line why it cannot (and deletes nothing), or asks, naming the hive, and the district is read again once the hive is gone.

**Delete hive** (a red pill under the wiring of a hive at rest) asks first, naming the hive, and says it cannot be undone. It deletes only that hive from this device. It is refused, with a plain reason and nothing deleted, while a run of it is live, when another hive uses it as a circuit, and when it came from a package (remove the package in the Store). Past runs are kept: they stay in history and open read-only under the title "Deleted hive", showing the tasks the run recorded, and can be viewed but not resumed or re-run. Startup skips a latest run whose hive is gone and starts empty. Your memory, repositories, runs and other hives are never touched, and no repository operation is involved. Afterwards the app returns to the hives list.

## Zoom levels

The hive's camera follows the selection instead of asking you to zoom and pan (`TerrariumFocus.kt`, `TerrariumCamera`; Build and Live). By default it shows the **Whole hive**. Selecting a creature (or grouping a cluster, which counts as one focus) starts a stack of views, innermost first, each fitted with padding and animated (instant with reduced motion). A view that is empty, or that shows the same creatures as the one before it, is skipped:

1. **Creature**: the creature with a little context.
2. **Neighbours**: it, the creatures feeding it and those it feeds.
3. **Path to the orchestrator** or **Path to the end goal**, whichever is shorter (a tie goes to the orchestrator). The orchestrator is the creature with the Orchestrator role, else the entry creature (nothing feeds it); the end goal is the nearest creature nothing else waits on.
4. The other of those two paths.
5. **Path to the active step**: the shortest path over strands to the nearest running creature (Live only).
6. **Path to the blocks**: the shortest path to the nearest creature waiting for approval, blocked or failed.
7. **Whole chain**: all its ancestors and descendants.
8. **Whole hive**.

**−** and the system Back step one view out; **+** steps back in through the views already passed. Selecting another creature starts again at Creature; tapping bare ground lets go of the selection and shows the whole hive. Creatures outside the view are dimmed, and the strands of its path are drawn in Yellow. A label by the control names the view (tap it to snap back to it). Pinching or dragging the ground moves the camera freely ("Free view") without changing the stack; stepping, or tapping the label, returns to the view. Drag empty ground to pan, pinch (or two fingers) to zoom and pan. A strand is cut by dragging across it (a drag that starts on a strand); a strand is drawn from a creature's tail.
