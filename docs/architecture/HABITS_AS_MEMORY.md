# Habits as memory: formation, correction, and overcoming

Status: **design; nothing here is built.** It amends [PROCEDURAL_MEMORY.md](PROCEDURAL_MEMORY.md) (§1, §5, §6) and the order of [the implementation plan](PROCEDURAL_MEMORY_IMPLEMENTATION_PLAN.md) (milestones 3, 4 and 7). Where this note and those documents disagree, this note is the direction; the rest stands. Memory rules it relies on are in [Memory-layer](../Memory-layer.md): condensation, contrast, deliberation, lineage banks, the size rule.

## 1. The principle

A habit is a memory. It forms the way memories form, it is corrected the way memories are corrected, and a bad one is overcome the way a person overcomes one. It is not a separate object that something proposes, validates and promotes.

Two things stay as they are:

- **Memory organizes; it does not judge.** The clerks fold repeated episodes together and mark where they differ. Which version is right is decided by a deliberation written by the conscious layer (an agent, or the keeper).
- **Models and the keeper write flags; the engine states facts. A flag informs; it does not forbid.** The offer of a habit carries facts the engine states (uses, outcomes, an open contrast, an override) and flags written by the models that used the habit or handled its results, or by the keeper. A flag never says not to use the habit. The model reading the offer decides.
- **Strength decides what is offered. Policy decides what runs.** A habit that has become strong is recalled first. Whether any step may run is still decided by the task and executor layer: mutating and privileged steps keep their approval gates however strong the habit is. Recall never executes.

## 2. Formation

A habit forms by repetition, with no promotion event.

~~~text
run 1 receipt ─┐
run 2 receipt ─┼─ episodes ─ condense (similar) ─▶ one habit memory ─▶ stronger with each use
run 3 receipt ─┘                                    skeleton + slots,    fading when unused
                                                    body in the sidecar
~~~

- **Episodes already exist.** Each finished system-executor task banks a redacted receipt as a contextual episode (opt-in, `proceduralTraceCaptureEnabled`).
- **Similar episodes condense** under the existing rules: same frame, same or synonymous filler. The condensed memory keeps the occurrence count, the time range and the weight, and the sources become history linked by `CondensedFrom`.
- **The habit memory is a skeleton plus an address.** The skeleton is the ordered steps (each a symbolic executor operation). The executable body stays in the procedure sidecar, content-addressed, because executable text never goes into a memory node. The memory holds a summary and the address.
- **Slots come from the variant register.** What differs across the repeated runs (a path, a branch, a target) is the filler. Each frame's register already lists its fillers with age, context and occurrence count. A filler that varies becomes a typed slot of the habit, and its register is the set of values the slot has taken. This replaces hand-declared parameter schemas.
- **Strength comes from use and from verified outcomes.** Using a habit strengthens it as any memory is strengthened by access. Weight counts runs whose outcome was independently verified more than runs that were merely reported complete. A repeated mistake is a pattern for the reasoner, never a stronger default (the existing rule for repetition).
- **Disuse fades it from default recall.** Nothing is deleted. A faded habit is still reachable by lineage.
- **Scope is the lineage bank, not the run.** Today a procedure bank is one workflow run, so nothing can repeat across runs. Habits live in the workflow's lineage bank (its own records plus its ancestors'), with other project workflows read-only, exactly as memories do.

## 3. Cues

A habit comes up when its **cue** appears: the context in which it has fired before. A cue is derived, not declared, from the same material memory already indexes: task cues, executor kinds, code symbols, the objective's terms, and the slot values seen. Recall matches cues against the current task. The cue is part of the habit memory and is shared by every version of it.

## 4. Correction

A habit is never edited in place.

1. **Noticing.** An execution of the habit's frame with a different outcome, a different step, or a failure is an episode that the divergence marker pairs with the habit: `Diverges`, same question, different answer. Both sides are recalled together.
2. **Deliberation.** The conscious layer reads both sides plus the verification evidence and writes a deliberation naming the version it judges correct (or that the habit is wrong here). No deliberation, no consolidation of a contrast.
3. **Absorption.** Consolidation absorbs the deliberation into the chosen memory as a **new version**. The old version becomes history, linked to the reason, and fades from default recall as the dispute fades with use.

This replaces the plan's validate-and-promote state machine for what a habit *is*. Version numbers stop being the identity: the lineage (`Supersedes`) is, which also removes the reuse of a number after a version is deleted.

## 5. Overcoming a habit

Correction after the fact is how a habit is first noticed to be wrong, and it is not yet how it is overcome. A habit that fires automatically is not stopped by learning it was wrong. It is stopped the way a person stops one: it happens by accident, enough times that each time has to be corrected; then the person begins to **anticipate** when it will come up, takes **deliberate control of that moment**, and does so again the next time, and the next, until the other behaviour is the habit.

~~~text
accident ─▶ correction ─▶ anticipation ─▶ controlled occurrence ─▶ repeat ─▶ new habit
 (habit fires,    (Diverges +    (its cue is     (the conscious layer      (each controlled   (the alternative
  outcome wrong)   deliberation)  watched for)     decides this time)        pass is an episode) consolidates)
~~~

| Stage | What exists | Rule |
| --- | --- | --- |
| Accident | The habit was offered or run and the outcome was wrong. | Recorded as an episode; paired with the habit by the divergence marker. |
| Correction | A deliberation: this habit is wrong in this cue. | Written by an agent or the keeper. A keeper's "stop doing that" is a deliberation the same way. |
| Anticipation | An **override**: the deliberation scoped to the habit and its cue, with the alternative (do X, or ask me). | The cue is checked at **planning and recall time, before dispatch**, so the moment is met ahead of time, not after the habit has fired. |
| Controlled occurrence | At the cue, the offer **shows the override** as a fact (§5.1): the deliberation's text, who wrote it, and the alternative. The habit is not hidden and not blocked. | The conscious layer is made to decide this occurrence knowingly, which is the control. It may follow the alternative or use the habit; either way the choice is an episode. |
| Repetition | Each controlled occurrence is an episode: what was decided and how it turned out. | Counted when the override was shown and the decision was made on purpose. A lapse (the habit ran without the override being read, or a controlled pass failed) is a new accident and starts the loop again, with the count kept. |
| New habit | After enough controlled passes without a lapse, the alternative condenses into a habit of its own (§2) and the override can retire. The old habit fades from default recall and stays as history. | The threshold is a setting, not a constant of the design. |

An override can only **inform or redirect**. It never grants authority, never makes a step runnable, and never lifts an approval gate. It is memory and cannot run anything.

### 5.1 Facts on an offer

The swarm gets a leg up from what memory already holds about a habit, stated where the habit is offered. These are **facts, not flags.** The engine states them from memory state, as it states `Diverges`; it does not write flags.

| Fact | Stated when | Carries |
| --- | --- | --- |
| Open contrast | A `Diverges` marker pairs the habit with a differing execution and no deliberation has resolved it. | Both sides' memory ids, the counts on each side, the pair summary. |
| Recent outcomes | The habit has executions in this cue. | How many of the last runs ended failed or were turned back, when, memory ids of the episodes. |
| Override | A deliberation scoped to this habit and cue exists (§5). | The deliberation's text and author (a model or the keeper), its date, the alternative, and the controlled-pass count so far. |
| Verification | Always. | How many uses were independently verified and how many were only reported complete. |
| Environment | The environment the habit formed in differs from this one. | What differs (tool or platform version, repository shape). |
| Last used | Always. | When the habit was last used. |

- **Stating a fact is noticing, not ruling.** Fact wording uses no judging word (correct, wrong, better, outdated), the rule already applied to divergence pair summaries. A deliberation quoted in an override is its author's judgment, named as theirs.
- **Offer, not block.** The habit stays in the offer with its facts. Facts never remove it, lower its authority, or change what policy requires to run it.
- **The habit can always be chosen.** As with a bad habit, nothing in memory takes the choice away. Choosing a habit against the facts shown is allowed and recorded as a decision, with the facts that were shown. If it goes well, that is evidence against the override that warned, and it pairs with the deliberation as a contrast that can be deliberated in turn. If it goes badly, the next offer's recent outcomes say so. The only thing that can stop a step is the task layer's own approval policy, which exists without memory and is not changed by it.
- **It teaches by repetition.** A model that keeps meeting an open contrast, bad recent outcomes and an override starts deciding on purpose, which is the controlled occurrence of §5. Reading the facts and setting them aside is still a decision made knowingly, and is recorded as one.

### 5.2 Flags written by the models that use a habit or handle its results

A flag is written by a model or by the keeper, never by the engine. The engine states facts (§5.1). A keeper's decision to change what models do is a deliberation or an override and is shown as one; a keeper's own warning on a habit is a flag (§5.4). Two kinds of model can write one: the model that **used** the habit, and a model that **handles its results**, which may be a different model that never saw the habit (the next task that consumes what the habit produced, or the reviewer that verifies it). The second often sees what the first cannot. Either adds its own flag or does not. Nothing makes it. What the next model sees is the record of both, with the source of each flag.

- **The flag.** The model's own words about what it just did, when they warn (for example "step 3 assumes a clean tree"). The model does not call anything to flag a habit: it reacts as it normally would, and a clerk recognizes whether the reaction is a flag (§5.3). A flag is a warning, never a prohibition. It is stored as a memory linked to the habit, attributed to its author (role, provider, task run), and scrubbed and bounded like any memory text. The engine writes the link on the clerk's recognition, so `MODEL_WRITABLE_RELATIONS` does not widen.
- **The counts.** Every offer shows raw numbers beside the habit and its flags, with flags split by source (by the model that used it, by models that handled its results, and by the keeper): **how many times it has been used** (the habit memory's occurrence count, with how many of those were independently verified) and **how many flags it carries** (by kind, with the newest few quoted). There is no score. The memory layer does not divide one by the other or rank by the result, and the facts of §5.1 sit beside them unscored; the model reading the offer starts forming its own judgment from the numbers, which is the point.
- **Silence is not approval.** A use with no flag counts as a use. It does not count as an endorsement, and it weighs less than a verified outcome.
- **Flags are memories.** Identical flags from different runs condense into one with an occurrence count. A flag that conflicts with another flag, or with a later deliberation, is a contrast and is handled by §4. A flag is never deleted by the habit's later success: success is counted as a verified use beside it (§5.1).
- **Data, not instruction.** A flag's text is recalled and shown as quoted, attributed data. It is never an instruction the memory layer or the offer gives the reader. A flag from a remote peer is marked untrusted until locally accepted. Authors are deduplicated per run so one run cannot stack flags.
- **No special path to authority.** A flag, however many a habit has, cannot hide the habit, block it, or change what policy requires to run it.

### 5.3 Recognizing a flag

A clerk, not the model and not the engine, recognizes whether a model's reaction to what it just did is a flag. The model only talks.

~~~text
offer H ─▶ model uses H (receipt matched to H, same session)      later task T2 receives H's results
                         │                                                  │
         engine opens a window: the user's next message(s)        engine opens a window: T2's messages while it handles them
                         │
         clerk reads the window ── caution about what was just done? ──▶ yes: keep the model's own words as a flag on H
                                                                        no: nothing is recorded
~~~

- **Which clerk.** The `CategoryClassifier`, with one more filing label, `caution`, beside the labels it already assigns for what a segment is (`requirement`, `preference`, `implementation state`, and so on). The label says what the speaker expressed, as `preference` does. It is not a verdict on the habit and never says the habit is wrong. A new clerk role is not needed.
- **What the engine decides, mechanically.** Whether a window exists and which habit it is about. There are two kinds. A **use window**: the model used H (a receipt matched to H's skeleton) in this session, and the window is the messages after the use up to a bound (a few messages, the next tool use, or the end of the task). A **results window**: a task that depends directly on the task that used H, or whose context carries artifacts that task produced (the existing artifact ancestry), and the window is that task's messages while it handles them, up to the same kind of bound. Direct consumers only by default. No window, no flag. A reaction outside a window is never a flag on H. Each flag records its source (`used` or `handled`) and the chain of task runs that binds it to H.
- **What the clerk decides.** One question: in these messages, does the model express a caution, difficulty or warning about the thing it just did, as opposed to routine narration? It answers flag or not. It keeps the model's own sentences, verbatim, and bounded. It writes nothing of its own and gives no reason.
- **What the clerk decides about a results window.** The same one question, asked of the results: does the model express a caution about what it received or how it came to be, as opposed to routine narration? The clerk cannot tell whether the caution concerns H or the material H worked on. That is why the source and chain are kept and the two kinds are counted apart, so the reader can weigh them.
- **A result can try to steer its handler.** A habit's output is untrusted data, and a handler could be led by it to write a flag (or not to). A flag from a results window carries the taint labels of the context that handler received, and one task run writes at most one flag per habit. A flag whose context carried untrusted-tainted material is shown as such. No flag from a window changes what the habit may do.
- **What the clerk does not decide.** Whether the caution is true, whether the habit is bad, which habit version it concerns beyond the engine's binding, or what should be done. A flag from a mistaken model is still a flag; the counts and the other flags let the next model weigh it. The clerk never infers a flag from silence or from outcome alone.
- **Programmatic first.** As with every clerk, a programmatic recognizer ships first: negation and hedge structure, the model's reference back to a step or an outcome ("failed", "had to", "assumes", "unexpected"), and a window tied to a use. A local model is added only if it beats that baseline on held-out sessions by more than noise, with the shortcut checks the retired orchestration specialists lacked: predict "not a flag" always, and predict "flag" whenever the outcome was a failure.
- **Training data.** Labels come from sessions where a later deliberation or a keeper confirmed or rejected a flag. Until there are enough, only the programmatic recognizer runs.
- **The model is told.** The offer says that a reaction after use may be kept as a flag on the habit, and a task that receives a habit's results is told which habit produced them and that its reaction may be kept the same way, so the behavior is not hidden from the model whose words are kept. Capture follows the existing opt-in for procedural memory.

### 5.4 The keeper can always flag it

The keeper can go back at any time, find a habit, and flag it themselves, in their own words. Nothing opens a window and no clerk is involved: an explicit flag from the keeper is a flag.

- **Any habit, any time.** Any version, including a faded one or one a deliberation has superseded. The keeper is not bound to a use or a results window.
- **Finding it from the result.** A result carries a pointer to the habit that produced it, through the same artifact ancestry the results window uses. From any task's result the keeper can follow "produced by habit H" to H and flag it there. A habit can also be found from the procedure library, where each habit shows its counts, facts and flags.
- **Source is shown.** A keeper's flag is attributed to the keeper and counted apart from model flags. It is a flag like the others: it informs, never blocks, and the habit can still be chosen.
- **Add-only.** A keeper can add a note that supersedes their earlier flag, and can always forget one under the existing erasure rules. Nothing else rewrites it.
- **Different from a deliberation.** To change what models do about a habit, the keeper writes a deliberation (or an override, §5). Both can exist on one habit.

## 6. Boundaries

- **Clerks never judge.** Folding, marking, summarizing, cue extraction and stating a fact are clerk or engine work. Writing a flag is a model's. Choosing a version, writing an override, writing a flag, and deciding that a controlled pass succeeded are the conscious layer's.
- **Sidecar for bodies.** Executable content is content-addressed in the procedure sidecar. A memory node holds the skeleton summary, the cue and the address. Nothing executable enters `MemorySnapshot`, and `MODEL_WRITABLE_RELATIONS` does not widen.
- **Privacy and erasure are unchanged.** Capture stays opt-in and structural. Forgetting a source episode removes habits that depended on it, as procedures are removed now.
- **Popularity risk.** Condensation lets the most common behaviour become the strongest. The guards are the divergence marker, outcome-weighted strength, and the rule that repetition is evidence, not truth.
- **Remote peers.** A procedure or override from a peer is an untrusted proposal until locally accepted. Duplex stays a transport.

## 8. Order of work

1. This note, and the trace additions (operation identity, slots, outcome). Nothing forms without them. **Built:** the receipt carries `operation`, typed `slots` and a `verification` field, and `ProcedureVerifications.of` derives verified or rejected from a reviewing task's verdict. **Also built:** a verification is recorded as a new receipt beside the original (`ProcedureTracePhase.Verification`, written by `ProcedureVerificationObserver` through the same opt-in sink), never as a rewrite. **Still open in this step:** give scripts and test commands a name through a host-supplied descriptor.
2. Formation from receipts. **Built (single-operation habits):** `HabitFormation.form` turns receipts into habits. The frame is the executor and the named operation; a use is one finished execution; the slots keep a register of every value they took; failed, verified and rejected uses are counted apart. A habit is offered at three uses, at `Low` strength (§9). `MemoryLayerController.formedHabits` reads the receipts of the workflow's lineage and the other runs of its project, read-only, so it pools only what memory recall already reaches. It runs nothing and writes nothing. **Not yet:** habits of several steps (an ordered sequence repeating across runs), writing a habit into the memory graph as a condensed memory with `CondensedFrom` edges, and per-step slots. The older explicit-proposal path (`ProcedureCandidateProposalService`) is unchanged and still has the two bugs found in review (a required parameter becoming optional when steps are merged, and a version number being reused after a delete); they are fixed when that path is replaced by formation, not patched twice.
3. Recall of habits by strength, offer only, with the counts (uses, verified uses, flags) and the facts that need only the divergence marker and the receipts (open contrast, recent outcomes, verification, environment, last used). Uses are the habit's occurrences from formation, so they need no invocation. The use window, the results window (direct consumers) and the programmatic `caution` recognizer ship here too. No execution. **Built:** `HabitOffers` picks the offered habits whose operation a task names (at most three) and renders their counts and facts as a "Habits" prompt block, which `recallForPrompt` adds only while procedural capture is on and a habit matches; the text states facts and never tells the reader what to do. Facts built: uses, completed and failed, reviewed (approved, turned back, not reviewed), the newest three uses, last used, strength. `CautionRecognizer` (programmatic, conservative: a warning cue plus a reference back to the work) keeps a model's own sentences; `HabitFlagObserver` runs it on an agent task's output when that task depends directly on a finished system executor and records at most one flag per agent task run per habit, with its source (`Handled`), author and whether untrusted content was in front of it. A flag is a `Flag`-phase receipt, so it is durable, deduplicated, bounded and scrubbed like the rest, and is never counted as a use. `MemoryLayerController.flagHabit` records the keeper's own flag on any habit (5.4). The offer shows flag counts by source and quotes the newest three as data. **Not yet:** the use window (it needs a model to use a habit, which waits on invocation), the open-contrast and environment facts (they need the divergence marker over habits and a tool fingerprint), a clerk model for `caution` beyond the programmatic one, and any screen for the keeper's flag.
4. Correction: `Diverges` pairing of habits with differing executions, deliberation records scoped to a habit, absorption into a new version. **Built, on receipts:** a habit's current version is computed from its receipts, so nothing is edited in place. *Open contrast* is the fact that the same configured values have both completed and been failed or turned back; different values are only variation, as the slot register shows. A *deliberation* is a `Deliberation`-phase receipt (author a role id or `keeper`, text up to 400 characters, outcome `Stands` or `Superseded`), recorded by `MemoryLayerController.deliberateHabit`. `Stands` answers the contrast, and only something turned back after it reopens it. `Superseded` closes the version: uses before it are history (`earlierUses`, not counted), the version number rises, and the habit starts again from what is done after, so an alternative is offered after the same three uses as any new habit. The offer states open contrasts, the version, and the latest decision as data, and says when no decision has been written. **Also built, a model-facing way to write a decision:** an agent states one line, `HABIT-DECISION: <operation> | stands|supersedes|overrides | <reason>` (an override adds ` | <instead>` and optionally ` | <alternative operation>`), in the same spirit as the `VERDICT:` line of a gate. `HabitDecisions.parse` reads it (at most three per text; a line that does not parse is ignored, never guessed at), and `HabitDecisionObserver`, called from the same place as the other observers, records it as a Deliberation receipt authored by the task's role, once per task run and operation. **One rule guards it: a task that had untrusted content in front of it records nothing.** A flag may carry a taint mark because a flag only informs; a decision can end a version or put an override in front of every later use, and text read from outside must not be able to do that. The offer does not carry the format, because an offer states facts and never instructs; `HabitDecisions.INSTRUCTION` is a sentence a task's objective may carry (opt-in, like the gate's), and nothing adds it by itself. **Not yet:** a `Diverges` edge in the memory graph.
5. Overcoming: overrides and their place among the facts, anticipation at planning and recall time, controlled-pass counting, consolidation of the alternative. **Built:** an override is a third decision outcome (`Overrides`) on the same `Deliberation` receipt, with the alternative in the author's words and, optionally, the alternative as a named operation. The habit is not hidden or blocked: it stays in the offer, and the offer shows the override first with what to do instead, how many times the habit has been used since, and how many times the alternative has. A task that names the habit's operation meets the override when its prompt is built, which is before dispatch, so anticipation is the offer itself. An override is shown even before the habit has been offered. **Controlled passes are the alternative's uses:** the alternative is just a new habit, so three uses of the named alternative operation make it a habit of its own and retire the override (it stays as history), with no separate counter to keep; a use of the old habit after the override is shown beside it as a lapse that starts nothing over and loses nothing. An override with no named alternative operation never retires by itself; a later `Superseded` decision ends it with the version. A model may write an override with the decision line of step 4, under the same untrusted-content rule.
6. Governed reflex invocation, then the habit runner, behind the existing gates. **Built (single operations):** `HabitInvocation.propose` turns a formed habit into an ordinary `TaskDefinition` and runs nothing; `MemoryLayerController.proposeHabitTask` wraps it. The executor is rebuilt from the named operation (GitHub Action, deployment, repository operation, external service, nested workflow); a git ref and inputs come from the caller and are accepted only as the short typed values a receipt keeps; the habit's slot register is advice and is never copied in, because a receipt cannot restore an input's exact name. The task carries a human-approval policy, but the engine reads a task's policy only to let an agent proceed past its plan, so the policy alone does not hold a system step (a test runs the proposal ungated and both steps dispatch unattended). The hold is a separate human-approval task, which `WorkflowCompositionService.addProposedTasks` puts in front of every proposed step; a proposal run any other way is not gated. Once added, the task goes through the workflow engine, its executor integrations, its approval gates and its context-taint gate like any other task, so no executor, permission or shortcut is added. A habit placed on another node, or an operation that names nothing rebuildable, is refused rather than guessed. A standing override is named in the task's objective, not hidden from it. When the task runs, its receipt is a use, so the loop closes by itself. **Habits of several steps, built as sequences:** `HabitSequences.form` finds named operations that finished one after another in the same order in at least three runs (consecutive finished executions only; a stretch where two finished at the same instant is skipped because its order is unknown; a shorter sequence inside a longer one seen in exactly the same runs is left out). The order is the order they finished, as observed, and nothing claims one step caused the next. The offer lists a sequence, with how many runs and how many of them had every step clean, when a task names its first step, and says the order is observed and not a dependency. `HabitInvocation.proposeSequence` (and nothing else) turns a sequence into ordinary chained tasks: each depends on the one before so they run in the observed order, each asks for a person's approval first, and any step that cannot be rebuilt, or was placed on another node, refuses the whole proposal. **Checked, and no separate runner is needed so far:** run through the real runtime, the chained tasks stop at each approval and run in the observed order, and after a restart (a new coordinator over the stored run, `resume`) a finished step is not dispatched again and the sequence stops at the next approval (`HabitProposalRuntimeTest`). **Not checked:** resuming while a step is still running at the outside service, and what a person sees when a middle step fails (the engine's existing retry and escalation policies apply, because a proposed task is an ordinary task); a screen to choose where a proposed task goes. **Built:** the Habits panel has a **Propose a task** action on each habit that shows what the task would be (its name and objective, that it asks a person's approval first, and that it is added to no workflow), or why none was proposed; it adds and runs nothing. **Built under that screen:** `WorkflowCompositionService.addProposedTasks` appends proposed tasks to a workflow after the tasks chosen, refuses an id already in use, a repeated id or a task to follow that does not exist, validates the graph, and returns the result without saving, like the service's other methods; each added task keeps its approval policy, and every proposed step gets its own human-approval task right before it. That is the engine's way of holding a system step, and the graph validator separately requires one ahead of any repository mutation (found when a proposed merge step was refused by an ordinary workflow). `HabitProposalRuntimeTest` runs the result through the real runtime: nothing proposed dispatches before its approval is completed, and the steps run in the observed order.

Each step is testable without the next. Acceptance for the whole: a habit forms from repeated runs without any promotion step; a differing execution surfaces beside it; a deliberation produces a new version and keeps the old as history; after an override, the cue yields the habit's offer showing the override (not hidden, not blocked), and enough knowing passes consolidate the alternative; no step ever runs without the task layer's own approval.

## 9. Decided

- Models write flags in their own words, and a clerk recognizes that a reaction is one (§5.3). The keeper can always go back, find a habit and flag it themselves (§5.4). The engine states facts; a keeper's decision to change what models do is a deliberation. Flags and facts are informational: none becomes a required acknowledgement or a block, and the habit can always be chosen (§5.1). Approval gates on mutating and privileged steps are the task layer's and are unchanged.

- A habit is offered at **three uses**, at **low** strength. There is no higher level yet; more are added when the data shows where one habit differs from another.
- An alternative to a habit consolidates after **three** knowing passes, the same number, because the alternative is just a new habit (`HabitSettings`).
- Recording a verification is folded into formation: it is a receipt, not an update.

## 10. Open decisions for the keeper

- Strength levels above low, and what moves a habit up or down them.
- Whether habits should form across all of a project's runs (as built, read-only) or only along a run's own lineage.
- Whether read-only reflexes may ever be offered by strength alone, without a person choosing.
- Where anticipation runs first: the planner, the Context Packer, or both.
- Whether a keeper's override carries more weight than an agent's, and how long an override lives with no cue match.
- How fast an unused habit fades, and whether fading differs for mutating habits.
- How far down the consumers a results window reaches (direct consumers only is the default), and whether a verifier's flag is shown apart from other handlers'.
- Whether `caution` extends the `CategoryClassifier` (suggested) or becomes its own clerk, and how wide the window after a use is.
- How many model flags an offer quotes, the length limit of a flag, and whether flags from peers show at all before they are accepted.
- Whether the offer shows flag counts only for the current cue or also across all cues.
- **Built as defaults, to be corrected by what they show.** Each item below was built without data behind it, on the keeper's instruction to build it and fix it when it turns out wrong. For each: what it does, what it is not, and what result would show it is wrong. The Habits panel opens with the counts (habits, offered, uses, failed uses, flags by source, open contrasts with no decision, standing overrides, replaced habits, sequences) so that is visible.
  - *Environment fact.* A receipt names the repository (`owner/name`) it was done in; the offer says "Done in a/b (3), c/d (1)."; the banked episode says "Environment: a/b.", so memory's own consolidation sees one frame in two places, which is where a `Diverges` link for environment comes from (no graph code of ours). It is the repository, not a tool version: a workflow file changing under the same name is not seen. *Wrong if:* habits that fail in one repository and pass in another are not showing it, or repository names are usually missing from receipts.
  - *Use window.* An agent that a finished executor task depends on directly is taken to be the model that prepared or chose that run; its cautions about the operation are flagged with source `used`. It is not a record of a model being offered the habit (the offer does not leave a trace of who read it). *Wrong if:* `used` flags are mostly the same sentences as `handled` ones, or are about things that have nothing to do with the habit.
  - *Clerk for `caution`.* `CautionClerk` is a seam, `MemoryRuntimeBridge.cautionClerk`, null by default. When the programmatic recognizer keeps nothing from an agent's output, the clerk is asked about the sentences set aside (`CautionRecognizer.candidates`, at most six) and keeps the ones it labels cautions, verbatim. It can only add. No model is wired to it yet; the app supplies one when a model for the job exists. *Wrong if:* the candidates the recognizer sets aside, read by the keeper, are mostly cautions (the recognizer is too strict) or mostly not (a clerk is not worth having).
  - *Writing a habit into the memory graph.* Not a second store. Receipts are already banked as episodes (`MemoryLayerController`, `contextualSummary`), including flags and decisions, so memory already condenses and diverges them by frame and filler; the habit is the counted view of those episodes. *Wrong if:* recall of an episode misses what the counted habit shows; then a condensed habit memory with `CondensedFrom` edges is worth writing.
  - *Refinement-level adapters* (`tools/refinement_training`). `train_level.py` trains one level and judges it against the copy and constant baselines on held-out ladders; it refuses an unready level unless told, and marks the result. Its torch path has not been run. *Wrong if:* a level scores well but does not beat the best baseline by more than the noise margin, which is the retired orchestration specialists' failure again.
- Where a proposed task goes: which workflow, after which tasks. **Built as a default:** after **Propose a task** (or **Propose these in order** on a sequence), the panel lists the workflows the keeper authored and adds the proposal to the one chosen, after the tasks nothing else waits on, each step behind its own approval task (`WorkflowLibraryHost.addProposedTasks`). An installed workflow is never changed. A proposal added twice gets fresh ids (`-2`, `-3`). The workflow is saved only if the graph validates. *Wrong if:* the keeper wants it after a particular task, or in a workflow they did not author; then the choice of predecessor, or a copy of the installed workflow, is what to add.
- Whether a model's decision should require that it was offered the habit (as built, any task without untrusted content may decide about any named operation), and whether `HabitDecisions.INSTRUCTION` should be added to a task's objective by default when its offer carries an open contrast (as built, nothing adds it).
